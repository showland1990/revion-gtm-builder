# PLG acquisition engine

> The job is not more traffic. It is more right-fit users reaching a product experience capable of activating them.

Read `gtm-context.md`, `plg-model.md`, and the messaging house if present.

## Separate demand types

### Existing demand
User already knows the problem/category: search, comparison pages, integration directories, marketplaces, review sites, GitHub/package ecosystems.

### Created demand
User needs education or a new point of view: founder content, technical education, community, benchmarks/research, events, social, category narrative.

### Product-distributed demand
The product creates discovery: shared artifacts, collaboration, public pages, invites, generated outputs, API/open-source ecosystem, templates, integrations.

## Channel-fit interview

For each channel ask:
1. Does the primary ICP already use it?
2. Is the pain present when they are there?
3. Can our product/proof be demonstrated naturally?
4. Is intent high or low?
5. Can we instrument downstream activation?
6. Is the channel repeatable?
7. Does it scale economically?

## Channel scorecard

Score:
- ICP density
- intent
- speed to learn
- credibility fit
- cost
- scalability
- activation quality
- retention quality

Do not rank on cheap clicks.

## Acquisition quality metric

For every source track:
`Visitors → Signups → Activated → Retained → Paid/PQL`

A channel with fewer signups but much higher retained activation can be superior.

## Landing architecture

Map intent to landing experience:
- problem intent → problem/use-case page
- alternative intent → comparison
- integration intent → integration page
- product intent → homepage/pricing
- developer intent → docs/quickstart/repo

CTA should match readiness: try, install, run sample, connect integration, or book evaluation.

## Output

Add acquisition model to `plg-model.md`: primary channels, demand type, landing path, CTA, expected activation path, measurement and first experiments.
