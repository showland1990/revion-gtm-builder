# Start here

> Start small enough to be useful immediately, then go deep only when the business needs it.

## First-run behavior

If `docs/gtm-cofounder/founder-brief.md` does not exist:

1. Scan existing product/repo context briefly when available.
2. Ask the five core questions one at a time:
   - What does the product do, in one plain sentence?
   - Who exactly is it for?
   - What do they use today instead, and why choose this?
   - What is the current stage/traction?
   - What is the strongest provable asset?
3. Preserve the user's language.
4. Tag material beliefs:
   - `[validated]`
   - `[observed]`
   - `[inferred]`
   - `[assumption]`
5. Write `docs/gtm-cofounder/founder-brief.md`.

## Then choose the path

Ask what outcome they want, not which skill they want.

### Fast founder diagnosis
If they need the next move:
→ `strategy-and-roadmap`

### Complete GTM build
If they want to build PLG + sales-led + marketing + RevOps:
→ `gtm-foundation`
→ `foundation-review`
→ `strategy-and-roadmap`

### Established GTM team
If they already have customers, pipeline, analytics, CRM, and multiple GTM functions:
→ inspect existing artifacts
→ use `gtm-foundation` only to fill gaps/contradictions
→ `foundation-review`
→ `strategy-and-roadmap` in GTM Team Mode

### Specific problem
If the user arrives with a concrete symptom:
→ `gtm-orchestrator`

## Preserve the original early-stage discipline

Do not force a full commercial interview on a founder who only needs a useful next step.

If assumptions dominate:
→ `talk-to-users`

If ICP is fuzzy:
→ `who-is-this-for`

If the first-run leaks:
→ `time-to-first-value`

If early distribution is unknown:
→ `first-50-users`

The expanded system deepens the original workflow; it does not replace it.
